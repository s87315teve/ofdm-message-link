# 各 MCS 的 OTA UDP throughput 上限

量測對象是這個專案的 `tx_app` 與 `rx_app`。量的是**真實 OTA** 下，從發送端 UDP `:52001` 進、到接收端
UDP egress 出的 **UDP payload throughput**。兩個 app 都用預設參數原樣啟動，本資料夾只有量測腳本與這份報告。

> 這是同一張桌上的短距離、低功率量測，使用選用的 1.2 GHz profile
> （`configs/profiles/usrp_ota_1p2ghz.yaml`），**不是專案現在的預設頻率**。重現前請先確認你所在
> 場所可用的頻段與功率；不確定時改用 cable 加 attenuator。

這份報告同時是一個範例：實驗怎麼設計、指標怎麼定義、哪些結論有數據支持、哪些沒有。

## 1. 結論

**datagram 固定為 968 bytes**（剛好一個 PHY frame、不 fragment）；設備為 N210 → NI USRP-2901，1.2 GHz、5 MS/s，
TX gain 5 dB、RX gain 15 dB：

| MCS | 格式 | 無遺失 UDP throughput 上限 | 60 秒確認（上限的 97%） | 限制因素 |
|---:|---|---:|---|---|
| 0 | QPSK Turbo r1/3 | **1.71 Mbit/s**（220.6 datagram/s） | 1.657 Mbit/s，0 / 12,840 遺失 | TX airtime |
| 1 | QPSK Conv r1/3 | **1.73 Mbit/s**（223.0/s） | 1.673 Mbit/s，0 / 12,960 | TX airtime |
| 2 | QPSK Conv r1/2 | **2.47 Mbit/s**（318.4/s） | 2.393 Mbit/s，0 / 18,540 | TX airtime |
| 3 | QPSK Uncoded r1 | 沒有無遺失的操作點 | 3.465 Mbit/s，遺失 0.51% | SNR（無糾錯），RX burst 處理速率 |
| **4** | **16QAM Turbo r1/3** | **3.10 Mbit/s**（399.9/s） | **3.005 Mbit/s，0 / 23,280** | TX airtime |
| 5 | 16QAM Conv r1/3 | 沒有無遺失的操作點（最高約 3.13–3.17 Mbit/s） | 3.041 Mbit/s，遺失 0.085% | SNR |
| 6 | 16QAM Conv r1/2 | 沒有無遺失的操作點（最高約 4.1 Mbit/s） | 3.330 Mbit/s，遺失 4.47% | SNR，RX burst 處理速率 |
| 7 | 16QAM Uncoded r1 | 不可用（約 90% 遺失） | 0.240 Mbit/s，遺失 90.1% | SNR |

- **MCS 4 是這組設備的最佳選擇**：無遺失上限約 3.10 Mbit/s，以 97% 負載連續 60 秒 0 遺失。
- MCS 0、1、2、4 的上限**完全由 TX airtime 決定**，而且可以用公式精準預測（見[第 4 節](#4-上限從哪裡來)）。
  實測的飽和值和預測值差距在 0.1% 以內。
- 接收端的 effective SNR 不論 gain 怎麼調，都停在約 **17 dB**。MCS 3、5、6、7 在這個 SNR 下都有 CRC
  失敗，所以做不到無遺失。
- 提高 TX gain 會**更糟**：TX 15 dB 時連 MCS 4 都掉 11.6%（RX overflow），詳見[第 5.3 節](#53-tx-gain-的影響)。
- 超過上限時 link 不會崩潰：goodput 停在上限值。多出來的 datagram 會在 TX 的 ingress queue（256 格）
  **被默默丟掉**，latency 從約 60 ms 升到 0.7–1.3 秒。

## 2. 證據邊界

- 這是**單向 UDP** 量測，**不是** `iperf3`、TCP、雙向 TDD 或 ARQ 的結果。
- **這次沒有用到 B210**。發送端是 N210 + CBX，所以結果**不能**當作 B210 驗證。
- 所有結果都只來自**同一個 bench 幾何**。antenna 的位置和距離沒有量測，測試期間也沒有移動。
- 1.2 GHz 落在 1164–1300 MHz 的 GNSS 分配頻段內，所以維持低功率（TX gain 最高只試到 15 dB，
  CBX 上限是 31.5 dB）。
- 表中的 effective SNR 是 decision-directed 值，只計算成功解出的 burst（最近 64 個），接近失效門檻時會偏高。
  它只能當操作參考，不能當 link budget。

### 3.2 量測路徑

```
udp_load.py ──UDP :52001──▶ tx_app ──OTA 1.2 GHz──▶ rx_app ──UDP :52022──▶ udp_load.py
 (送出端)                   N210                   NI2901                  (收回端)
 固定速率送出                TX 5 dB                RX 15 dB                逐 byte 比對
 序號 + 時間戳 + 內容                                                        去重、算 latency
```

- [`udp_load.py`](udp_load.py) 在同一個 process 裡同時負責送和收。每個 datagram 前 20 bytes 是 header
  （magic、run id、序號、送出時的 `CLOCK_MONOTONIC`），其餘內容由序號決定，所以收回端不必保留副本，
  也能**逐 byte 驗證**。長度或內容不對算 `corrupt`，重複收到算 `duplicate`。這次所有 run 的
  `corrupt`、`duplicate` 與亂序都是 0。
- 送出端以固定間隔送（落後時立刻補送，不會集中爆發）。所有 run 的最大落後都不超過 5.3 ms，送出速率本身不是瓶頸。
- [`sweep.py`](sweep.py) 負責啟動 `rx_app`（`--stats-log`）與 `tx_app`（`--mcs-index N`）。每個量測點前後
  各讀一次 RX 的 stats log，把兩次的差當作這個點的計數。它也記錄 TX／RX 的 CPU 用量，以及 TX log 裡 UHD
  的 `U`／`L`／`S`／`O` 標記。
- TX 每換一個 MCS 就重新啟動（`--mcs-index` 是啟動參數）。RX 在第一輪掃描中一直保持運作。

### 3.3 指標定義

| 指標 | 定義 |
|---|---|
| Offered | 送出的 UDP payload bits ÷ 送出時間 |
| Goodput | 通過逐 byte 驗證的 UDP payload bits ÷ 送出時間（payload 含 20-byte header，也就是應用程式實際拿到的 bytes） |
| **Steady goodput** | 在「開始 2 秒後」到「停止送出」之間**到達**的 datagram ÷ 該時段長度。過載時，停止送出後 queue 還會繼續排空，用到達時間計算才不會高估 |
| 遺失率 | (送出 − 送達) ÷ 送出 |
| 遺失來源 | `payload decode 失敗`（空中 CRC／decode 失敗）；`missing_bursts` 扣掉 CRC 失敗之後，是完全沒被看到的 burst（通常是 RX overflow 丟掉的 samples）；UDP 遺失扣掉 `missing_bursts`，是在 TX ingress queue 被丟掉的 |
| Latency | 同一台主機、同一個 process 裡的 `CLOCK_MONOTONIC` 相減，所以不需要跨主機對時 |
| 95% 區間 | Wilson score interval |

> 第一輪掃描中，TX 每次重新啟動 PHY sequence number 都會重新起算，所以每個 MCS 的**第一個點**
> `missing_bursts` 會多算一次很大的跳號（例如 30,329）。那些點的遺失來源改用 CRC 失敗數判斷。

## 4. 上限從哪裡來

每個 burst 在空中佔用的時間 = OFDM burst 本身 + `UhdSampleSink` 在前面加的 **250 µs zero settle guard**
\+ burst 之間的 **20 µs gap**（`transport.py` 的 `UhdSinkLimits`，用來避開 front end key-up 的暫態和
`tx_time` late）。所以 TX 的服務速率是：

```
service_rate = sample_rate / (burst_samples + 1,250 + 100)      (5 MS/s 時)
UDP 上限     = service_rate × datagram_bytes × 8
```

[`airtime.py`](airtime.py) 用這個專案自己的 encoder 算出每個 MCS 的 `burst_samples`（不需要硬體）：

| MCS | 968-byte burst（samples） | Burst airtime | 只算 airtime 的上限 | **含 guard/gap 的服務速率** | **實測飽和 steady goodput** |
|---:|---:|---:|---:|---:|---:|
| 0 | 21,312 | 4.262 ms | 1.817 Mbit/s | 220.6/s = **1.709** Mbit/s | **1.709** |
| 1 | 21,072 | 4.214 ms | 1.838 | 223.0/s = **1.727** | **1.727** |
| 2 | 14,352 | 2.870 ms | 2.698 | 318.4/s = **2.466** | **2.466** |
| 3 | 7,632 | 1.526 ms | 5.073 | 556.7/s = 4.311 | 3.81–4.03（有遺失） |
| 4 | 11,152 | 2.230 ms | 3.472 | 399.9/s = **3.097** | **3.098** |
| 5 | 10,992 | 2.198 ms | 3.523 | 405.1/s = 3.137 | 3.13–3.17（有遺失） |
| 6 | 7,632 | 1.526 ms | 5.073 | 556.7/s = 4.311 | 3.85–4.10（有遺失） |
| 7 | 4,272 | 0.854 ms | 9.064 | 889.4/s = 6.887 | ≤ 0.85（約 90% 遺失） |

- 對 MCS 0／1／2／4 來說，每個 burst 固定多出的 0.27 ms 就是實測飽和值比純 airtime 上限低 6–11% 的原因。
  burst 越短，這段固定開銷的比例越大：MCS 7 如果能用，也只會剩 airtime 上限的 76%。
- 這個模型也和先前 3.8 GHz／B210 的量測一致：MCS 4、900-byte、400 burst/s、2.88 Mbit/s，
  那次的 400 burst/s 就是同一個天花板（見 [docs/08-measurements.md](../../docs/08-measurements.md)）。

  過關的 margin**。
- 代價是 RX 開始 overflow、丟掉 samples，連原本乾淨的 MCS 4 都在 50% 負載下掉了 11.6%。原因是 signal 太強時，
  RX acquisition 變慢、跟不上即時 sample stream。所以 **TX 5 dB／RX 15 dB 仍然是最佳設定**。
- SNR 停在約 17 dB 的原因（例如 phase noise、IQ imbalance 或其他 EVM floor）**這次沒有查明**。

### 5.4 datagram 大小的影響

| Datagram | MCS | 每個 datagram 的 burst 數 | 模型上限 | Offered | 結果 |
|---:|---:|---:|---:|---:|---|
| 968 B | 4 | 1 | 399.9/s = 3.097 Mbit/s | 388/s（60 s） | 3.005 Mbit/s，0 / 23,280 |
| 1472 B | 4 | 2（968 + 504 B） | 246.5/s = 2.903 Mbit/s | 230/s（20 s） | **2.707 Mbit/s，0 / 4,600** |
| 1472 B | 0 | 2 | 139.3/s = 1.641 Mbit/s | 135/s（30 s） | **1.590 Mbit/s，0 / 4,050** |
| 200 B | 4 | 1 | 1,054/s = 1.687 Mbit/s | 500/s（30 s） | 0.743 Mbit/s，遺失 6.75%（17 次 RX overflow） |
| 200 B | 4 | 1 | 同上 | 800/s（30 s） | 0.771 Mbit/s，遺失 38.3%（65 次 RX overflow） |

- **datagram 請盡量接近、但不要超過 968 bytes。** 超過就會 fragment 成兩個 burst，第二個 burst 也要付
  一次 guard／gap 和 header 的成本：MCS 4 的上限從 3.10 降到 2.90 Mbit/s（−6%）。
- **小 datagram 會碰到 RX 的 burst 處理速率上限。** 200-byte 在 500 burst/s 時 RX 就已經 overflow，遠低於
  TX 的 1,054/s。在這個 bench 上，RX 每秒大約只能穩定處理 **450–500 個 burst**，burst 很短時更少。
  先前在 3.8 GHz 離線量到的 decode 能力是每秒 1,000 個以上的 burst。兩者的差距符合
  「signal 越強，acquisition 越慢」的現象，但**這次沒有診斷**。

### 5.5 一次沒有解釋的異常

第一次跑 MCS 4／1472-byte（`size-m4-1472`）時，`tx_app` 已經 ready 也一直活著，但兩個速率點（230、239/s）
**一個 datagram 都沒送達**。TX 整個 process tree 的 CPU 只有 0.01 cores，RX 也完全沒有偵測到 burst，
表示 TX 根本沒有發射。

推測是前一個 TX 的 engine 子 process 還佔著 52001：ingress 用了 `SO_REUSEADDR`，兩個 process 可以
同時 bind 同一個 port。但在模擬 transport 下測試，`tx_app` 收到 SIGTERM 後 0.4 秒內就連同 engine
一起結束、port 也釋放了，所以這個假設**沒有得到支持**。同一組設定馬上重跑（`size-m4-1472-b`）完全
正常（0 / 4,600）。**原因未查明**。這兩個點沒有列入上面的結果。

## 6. 建議

| 情況 | 建議 |
|---|---|
| 一般使用（這組設備與擺放） | **MCS 4**，968-byte datagram，長時間負載 ≤ 3.0 Mbit/s（約 390 datagram/s）。SNR 約 17 dB，比 MCS 4 需要的約 11 dB（3.8 GHz 的量測值）多出約 6 dB margin |
| SNR 掉到約 11 dB 以下（例如 antenna 移遠） | 退回 **MCS 0**（≤ 1.65 Mbit/s）或 **MCS 2**（≤ 2.39 Mbit/s） |
| 想要更高速率 | 目前**沒有可用的 MCS**：MCS 3／5／6 會持續遺失，MCS 7 不可用。要先解決 SNR 停在 17 dB 的問題，以及 RX 每秒 burst 數的上限 |
| 單向影像串流 | 延續影像 demo 的做法，把 bitrate 設在上限的 50–60%，例如 MCS 4 用 1.3–1.8 Mbit/s |
| 應用程式設計 | 發送端**不會回報丟包**：超過上限時，datagram 在 TX ingress queue（256 格）被默默丟掉，只能從接收端的序號缺口看出來。請在應用層自己限速 |

## 7. 沒有做或沒有驗證的事

- 沒有量 10 MS/s、不同的 antenna 距離，也沒有改 RX gain（只調了 TX gain）。
- SNR 天花板（約 17 dB）與 RX burst 處理速率上限（約 450–500/s）的根本原因都沒有診斷。
- 60 秒確認只做了一輪，沒有做 5 分鐘以上的長時間測試。
- 沒有修改任何程式，所以 guard／gap 的長度、ingress queue 會默默丟包這些行為，這次都只記錄、沒有處理。
- 第 5.5 節的異常原因未查明。

## 8. 重現

從 repository root 執行。`sweep.py` 會讓 USRP 發射，所以必須帶 `--enable-rf`：

```bash
conda activate ofdm-message-link
D=experiments/ota_udp_throughput
# 你的兩台 USRP 的 serial（uhd_find_devices 可列出），以及這份報告使用的 profile
RADIOS="--tx-serial <TX_SERIAL> --rx-serial <RX_SERIAL> --overlay configs/profiles/usrp_ota_1p2ghz.yaml"

# 1. TX 服務速率模型（不需要硬體）；可加 datagram 大小，例如 1472
python -m experiments.ota_udp_throughput.airtime

# 2. 第一輪掃描：8 個 MCS × 6 個速率 × 20 秒（約 25 分鐘）
python $D/sweep.py --enable-rf $RADIOS --out /tmp/ota-udp/sweep1 --duration 20

# 3. 60 秒確認，例如 MCS 4
python $D/sweep.py --enable-rf $RADIOS --out /tmp/ota-udp/c60-m4 --mcs 4 --rates 388 --duration 60

# 4. TX gain 與 datagram 大小
python $D/sweep.py --enable-rf $RADIOS --out /tmp/ota-udp/gain-tx10 --tx-gain 10 --mcs 4,5,6,3,7 --fractions 0.5 --duration 15
python $D/sweep.py --enable-rf $RADIOS --out /tmp/ota-udp/size-m4-1472 --mcs 4 --rates 60,230 --duration 20 --size 1472
```

`--tx-serial` 與 `--rx-serial` 必填；gain 預設是 `--tx-gain 5 --rx-gain 15`，RX egress 用 UDP 52022。
每個 `--out` 目錄會產生 `results.jsonl`（一個量測點一行）、`rx_stats.jsonl`、`rx.log`、`tx-mcsN.log`
與每個點的 JSON。原始量測資料不放進 repository。
