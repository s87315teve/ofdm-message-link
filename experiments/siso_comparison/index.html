OFDM link 架構對照 · SISO-master vs ofdm-message-link

SISO 為什麼看起來在低 SNR 比較穩？

我把兩個專案的 TX／RX 程式碼逐行讀過，再把 SISO 的 PHY 用 numpy 照原始碼移植，和你的 PHY 放進同一組 AWGN／multipath channel 裡掃 SNR。下面是兩個架構的差異、SISO 做了哪些強化，以及模擬量到的數字。

結論：SISO 的 PHY 其實沒有比你的強。在同樣的真實 SNR 下，它的 50% 成功點在 6.4 dB（AWGN）與 7.4 dB（multipath），你的 link 目前是 7.4 與 10.0 dB。差距來自你 RX 的兩個問題：Turbo decoder 拿到的 LLR 全部飽和，以及 header 只靠一個沒放大的 training symbol 做 channel estimate。兩個都只要改 RX。修掉之後，你的 link 在模擬中降到 3.5 與 5.5 dB，比 SISO 好 2–3 dB。另外兩邊顯示的 SNR 定義不同：你的 meter 比真實 SNR 低 3–5 dB，SISO 的幾乎等於真實值，所以拿畫面上的數字直接比會誤判。

後續（2026-11-01，improve-rx 分支）：這份報告指出的兩個 RX 問題都修了，而且只改接收端、wire format 不變。另外也做了第 07 節的 noise variance、channel 平滑、header 強化與 SNR meter，並降低 acquisition 門檻。兩台 Pluto 在 2.45 GHz 實測，同一份錄音用新舊 RX 各解一次：遺失率低於 1% 所需的 TX gain，MCS 0 從 −10 dB 降到 −20 dB、MCS 4 從 −7.5 dB 降到 −12.5 dB。即時跑真的 app，MCS 0 在 TX −20 dB 從 76–77% 遺失變成 0.8–1.3%。做法與數據見 experiments/rx_improvement/ 與 docs/08-measurements.md 8.7。

後續（2026-11-01，tx-v5 分支）：improve-rx 之後，MCS 0 在最低 SNR 主要是 preamble 沒抓到，只改 RX 已經不夠，所以 tx-v5 改了發送端（wire v5）：802.11a 的 L-STF 與兩個 L-LTF symbol、K=7 convolutional code 加 interleaver 的 SIG header、802.11 scrambler、LTE rate matching 的 MCS 8–17（含 64QAM），以及 A-MPDU aggregation。TX 只送 v5；RX 同時收 v5 與舊的 v1–v4。兩台 Pluto 實測，和同一天量的 improve-rx 比：遺失率低於 1% 所需的 TX gain，MCS 8（QPSK 1/3）是 −25 dB，比 improve-rx 的 MCS 0（−18.75 dB）低 6.25 dB；900-byte datagram 的 goodput 在 TX −5 dB 是 9.295 Mbit/s（MCS 17）、−15 dB 是 5.063 Mbit/s（MCS 12）。做法與數據見 experiments/tx_v5/README.md。

報告本身保留當時的分析與數字；下面只在處理鏈與建議清單加上修改後的狀態。

02 · 訊號長相

時間軸上的差異：SISO 每個 symbol 都能自己同步

SISO 一個 OFDM symbol 2304 samples · 0.72 ms @ 3.2 MS/s

CP 被切成兩段相同的 128 sample，所以同一段波形在一個 symbol 裡出現三次，可以做三組 correlation 相加。每個 correlation 長 128 sample，是你 Schmidl–Cox 半段（32 sample）的 4 倍，timing metric 的雜訊因此小約 6 dB。TX 一直在發，所以 RX 每 0.72 ms 就重新同步一次，沒有「錯過 preamble 就整包掉」這件事。

你的 一個 MCS 0 burst（900 B） 19 392 samples · 3.9 ms @ 5 MS/s

整個 burst 的成敗壓在開頭 400 個 sample 上：preamble 沒過門檻、或 3 個 header symbol 的 CRC 沒過，後面 231 個 payload symbol 再乾淨也收不到。而 header 的 channel estimate 來自一個跟 data 同功率的 training symbol，估計誤差和 noise 一樣大。

頻域上的 pilot 密度 示意，前 64 個 tone

SISO 每 7 個 tone 就有一個比 data 高 9 dB 的 pilot，每個 symbol 都有新的 channel 量測。你的 4 個 pilot 和 data 同功率，只用來修相位；振幅與每個 tone 的 channel 都來自開頭那一個 training symbol。

04 · SISO 的強化手段

它做了哪些事讓連線比較穩

以下每一項都附上原始碼位置，以及對照你的實作。標 gain 的是它真正賺到的地方，cost 是它為此付出、或留下的弱點。

連續發射，每個 symbol 自己同步

app/siso-uhd-tx.cc stream()
lib/ofdm_sym_acquisition.c

gain TX 的 stream thread 沒有資料時會送 dummy symbol，所以空中永遠有訊號。RX 每次取 2·2048＋256 個 sample，對 2048 個候選起點算三組正規化 CP correlation，直接取最大值。門檻是相對的（大於過去峰值 IIR 平均的一半），不會因為 SNR 降低就整個偵測不到。前端增益與 AGC 也一直處於穩態，沒有 burst 開頭的暫態。

cost 不能 TDD、不能多台共用頻道，閒置時照樣佔滿頻寬與功率。

你的：Schmidl–Cox 在 32 sample 上做 correlation，門檻 0.40 在 SyncConfig 註解裡寫明約對應 +4 dB。模擬中 SNR 0 dB 時 79% 的 burst 連 preamble 都沒抓到，1 dB 時還有 57%。

加強 comb pilot，每個 symbol 重估 channel

lib/reference_signal.c

gain 1905 個 tone 裡有 273 個 pilot，值是 (±1±j)·2，功率 8，data 只有 1，所以 pilot 比 data 高 9 dB。data tone 的 channel 由左右兩個 pilot 線性內插，每 0.72 ms 更新一次。Pilot SNR 高，channel 估計誤差遠小於 data noise，也能跟上 symbol 之間的變化。

gain 同一組 pilot 也拿來做整數 CFO：在 ±71 個 tone 範圍內找 pilot 能量最大的位移，可抓 ±111 kHz。便宜的 TCXO（如 Pluto 的 ±25 ppm，在 2.4 GHz 就是 ±60 kHz）也不怕。

cost pilot 吃掉 57% 發射功率，data tone 的 Es/N0 比平均 SNR 低 3 dB。

你的：一個和 data 同功率的 training symbol，在 52 個 tone 上各做一次 LS（estimate_channel），沒有平滑。等化後的 noise 約變成兩倍（−3 dB），header 就是用這個 estimate 解的。

DVB-T 式串接碼與三層 interleaver

lib/tx_encoder.cc, reed_solomon.c,
convolutional_codec.cc, interleaver.cc

gain 內碼 K=7 (171,133) r1/2 convolutional（tail-biting，沒有 tail 開銷），外碼 RS(204,188) 可修 8 個 byte。中間的 byte interleaver 把 Viterbi 的連續錯誤打散到不同 RS symbol，bit interleaver 把 frequency-selective fading 打散到不同 trellis 位置。Energy dispersal（PRBS 擾碼）避免重複資料造成頻譜尖峰。

cost RX 用 qpsk_demap_hard 加 decode_Hard_SSE2，是 hard decision，比 soft Viterbi 少約 2 dB。程式也算了 symbol interleaver，但送出去的是沒交錯的版本（post_symbol_map /*post_interleave3*/）。

你的：Turbo r1/3 理論上強很多，正確 soft 輸入下 QPSK 約在 0 dB 附近就能解。問題出在送進去的 LLR，見下方第 05 節。

沒有獨立的脆弱 header

lib/packet_fragmentation.c

gain MCS 固定，RX 不必先解 header 才知道怎麼解 payload。12 B 封包標頭（sync 0x47、封包序號、片段序號、長度、port、timestamp）就放在 188 B 裡，和資料一起受 RS＋conv 保護。

你的：96 bit × 3 次重複只有約 4.8 dB 的能量增益、沒有 coding gain，而且要 96 bit 全對 CRC 才過。加上 channel estimate 的 3 dB 損失，模擬中它是整條 link 最先失效的地方，和 docs/08-measurements.md 8.5 節「遺失的 burst 幾乎都是 header 解不出來」一致。

錯誤單位小

lib/config.h

gain 一個 symbol 就是一個獨立的 188 B 區塊。短暫衰落只會掉幾個 0.72 ms 的 symbol，對 H.265 影像串流比較溫和。

你的：MCS 0 的 900 B burst 長 3.9 ms，中間任何地方出事整包都掉。

較窄的頻寬、較長的 CP

app/siso-*-tx.cc（rate 3.2）

gain 3.2 MS/s 收進來的 noise 比 5 MS/s 少 1.9 dB、比 10 MS/s 少 4.9 dB；同樣的發射功率與距離，SISO 的 SNR 就比較高。這是實機上最直接的差距，和 PHY 設計無關。80 µs 的 CP 也可以容忍很長的 multipath（你的 3.2 µs 在室內足夠）。

cost 1.56 kHz 的 subcarrier 間距對相位雜訊與 Doppler 敏感得多；它靠每個 symbol 重新估 CFO 與 channel 才撐住。

05 · 模擬

放進同一個 channel 比

怎麼量的
  • 你的：直接呼叫 repo 裡的 encode_burst／decode_burst（含原生 Turbo decoder），900 B MCS 0 或 MCS 4 frame，每個 SNR 150 個 burst。
  • SISO：把 lib/ 的 TX 鏈與 RX 的 MNC 同步、整數 CFO 搜尋、pilot 內插、hard Viterbi、RS 判斷逐行移植成 numpy，連續送 80 個 symbol，用 siso-rx 的串流迴圈收。RS 成功與否以「≤ 8 個 byte 錯」判定。
  • Channel：AWGN，或 5-tap multipath [0.82+0.13j, 0, 0.21−0.17j, 0, 0.08j]；兩邊都加 10 kHz CFO。
  • SNR 的定義兩邊相同：訊號在空中時的平均功率 ÷ 整個 sample-rate 頻寬內的 noise。
  • 沒有模擬：相位雜訊、IQ imbalance、ADC 量化、AGC、外部干擾。實機的門檻會比這裡高幾 dB。

畫面上的 SNR 不能直接比

橫軸是模擬設定的真實 SNR，縱軸是各自 RX 會印出的數字。SISO 用 CP correlation 算 ρ/(1−ρ)；你的是解碼成功 burst 的 decision-directed EVM，含 channel estimate 誤差，所以偏低 3–5 dB，而且只在解得出來時才有值。

同樣的接收功率，誰的 goodput 高

橫軸是 C/N0（接收功率 ÷ noise 功率譜密度），這是發射功率、距離、天線固定時唯一公平的比法：SISO 用 3.2 MS/s，你的用 5 MS/s，各自的 SNR = C/N0 − 10·log10(sample rate)。縱軸是扣掉所有 header 後的 payload 速率上限 × 成功率。

SISO 用每個 symbol 的成功率計算（上限）；若 UDP 封包跨多個 symbol，缺一個 symbol 整包就不完整，實際會更低。你的 burst 速率以 airtime 計算，未含主機端 CPU 限制（實測 MCS 0 約 230 burst/s）。

06 · Throughput

每個 sample 花在哪裡

把一段 airtime 拆成各種用途。SISO 的 payload 佔比比你的 MCS 0 高很多：code rate 0.43 對 0.33、CP 只佔 11%、沒有 preamble／header／guard。代價是它固定在這一個操作點。你的 MCS 4 每個 sample 帶的 bit 比 SISO 多，但需要的 SNR 也高很多。

bit/sample × sample rate ＝ payload 速率上限。把你的 link 也降到 3.2 MS/s，MCS 0 只剩約 1.19 Mbit/s；SISO 在同頻寬下是 1.96 Mbit/s。

07 · 可以借鏡的地方

依效益排序的修改建議

把真實的 noise variance 傳給 soft demapper

在 RX 端估 σ²：用 preamble 兩個相同半段的差（r[n] − r[n+32] 的功率 ÷ 2）、guard tone 或 null subcarrier 的能量，或 pilot 殘差。估好後傳給 StreamingBurstDecoder(input_noise_variance=…)，或改成每個 burst 自己估。只改 RX，不動 wire format。

狀態：已完成。最後的做法不是只用 preamble 量熱雜訊：解出來的 header symbols 是已知的，用它們的誤差當 noise，連 channel 估計誤差與硬體缺陷都算進去。只用熱雜訊時 LLR 太有自信，在實機上反而多掉約 1%。

MCS 0 +2.2–2.7 dB
MCS 4 +4.8 dB

平滑 channel estimate

把 52 個 LS 值擬合成 CP 長度內的時域 channel（DFT-based／LS fit），或把 3 個 header symbol 解出來後當作已知 symbol 再估一次。SISO 的做法是加強 pilot，但那要改 wire format，也會吃掉功率。

狀態：已完成：52 個 LS 值投影到 20 個 tap。殘差太大時退回原本的 LS。

再 +1.7 dB

Header 改用真的 FEC

把 96 bit 用 K=7 r1/3 convolutional（你已經有 native Viterbi）或短 Turbo 編碼取代 3 次重複，並以 |H|² 加權 soft combining。重複碼幾乎沒有 coding gain，這一步可以讓 header 比 payload 更耐 noise，而不是反過來。

狀態：用只改 RX 的方式做到了：CRC 失敗時，從約 8 200 個合法的 header 中以 maximum likelihood 選最接近的。實測中 header 不再是遺失的原因。真的 FEC 或頻率分集要改 wire format，寫在 experiments/rx_improvement/tx-proposal.md。

tx-v5：改成真的 FEC。SIG 照 802.11a 的 SIGNAL field：K=7 r1/2 convolutional code（native Viterbi）、BPSK、CRC-16，再用 144-bit interleaver 把相鄰的 coded bit 分到相隔 9 個 data carrier、跨三個 symbol，這就是提案的「分散到不同頻率」。CRC 失敗就丟棄，不再用 ML 清單。實測在 MCS 8 的邊緣，SIG 失敗佔遺失不到 3%。見 tx-v5 報告 2b。

header +3 dB 以上（估計）

讓 SNR meter 可以和別人比

另外顯示 pre-equalization SNR，例如照 SISO 用 preamble 兩半的正規化 correlation ρ 算 ρ/(1−ρ)。現在的 EVM-SNR 比真實低 3–5 dB，又只在解碼成功時才更新，衰落時看起來還是很好。

狀態：已完成：畫面上的 SNR 改由 preamble 在 data carrier 的頻帶內估計，沒解出來的 burst 也算。Pluto 的 guard band 雜訊比 data carrier 高約 10 dB，所以只看頻帶內。

診斷

較長的 preamble 或兩段 training

Schmidl–Cox 半段從 32 拉長到 64 或重複兩次，timing metric 的雜訊降 3 dB，可以把門檻從 0.40 調低。第二個 training symbol 也讓 channel estimate 平均兩次。代價是每個 burst 多 80–160 sample（不到 1%）。

狀態：門檻已從 0.40 降到 0.25／0.30（空中雜訊最高 0.20）。現在 MCS 0 在最低 SNR 時主要是 preamble 沒抓到，加長 preamble 是下一步，要改 wire format，見 tx-proposal.md。

tx-v5：兩項都做了。Preamble 改成 802.11a 的 L-STF（160 sample，每 16 sample 重複一次，lag-32 metric 累加 128 個 product，是原本的 4 倍）加兩個 L-LTF symbol；channel estimate 用兩個 LTF symbol 平均，再做 20-tap 平滑。MCS 8 的邊緣不再是 preamble：遺失 1–20% 的區間約三分之二是 payload 解不出來。離線重解同一份錄音，LTF 平均與平滑各自值 1–1.5 dB。見 tx-v5 報告 2a 與 4.4。

acquisition +3 dB

補一個 r≈1/2 的 Turbo MCS

用 LTE 的 rate matching（puncture parity）在 MCS 0 與 MCS 4 之間補 QPSK r1/2、r2/3，就能在 SISO 的操作點拿到接近的 bit/sample，同時保有 soft Turbo 的增益。mcs_table.py 已經預留了 index 空間。

狀態：tx-v5 做了：LTE rate matching（TS 36.212，RV0）讓 code rate 可以是 1/3、1/2、2/3、3/4，而且剛好填滿整數個 OFDM symbol。新的 MCS 8–17 包含 QPSK r1/2、r2/3 與 64QAM。見 tx-v5 報告 2d。

Pluto↔N210 這種 link budget 吃緊的組合，2.5 或 3.2 MS/s 的 profile 會直接多 2–3 dB。最便宜、立刻可以試。
